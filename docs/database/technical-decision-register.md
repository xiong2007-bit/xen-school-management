## 1. Platform and environment recommendations

### TDR-01 — PostgreSQL/Supabase
**Recommend:** Supabase-managed PostgreSQL/Auth as the initial managed platform, because the project already proposes Supabase and needs relational integrity, auth integration and RLS. Verify actual PostgreSQL major version, extensions, region, free/paid tier limitations, connection pooling, backups, PITR and availability before selecting a plan.

**Alternatives:** self-managed PostgreSQL; other managed Postgres vendors.  
**Risk:** relying on a provider feature that is unavailable on the chosen plan/region.  
**Acceptance:** documented provider/version/region/tier and operational capabilities; database access strategy tested.

### TDR-02 — Region, tier, recovery
Do not select by cost alone. Evaluate user latency in Zimbabwe, provider region options, data protection, availability, capacity, maintenance, backups and cost. Region choice is a legal/privacy review item; Zimbabwe-first is not a blanket permission to host all data anywhere.

Before production, define:
- RPO (maximum tolerable data loss) and RTO (maximum restoration time) by data domain.
- Backup cadence and retention.
- PITR availability/retention.
- Independent encrypted backup/export and key access.
- Restoration drill frequency and evidence.
- Who can restore and who approves access.

**Proposed pilot target for discussion:** RPO 24 hours and RTO 24 hours for initial low-cost pilot; improve for finance/critical operational records if business requirements demand. This is a proposal, not an assurance or provider guarantee.

### TDR-03 — Database schema and exposure
**Recommend:** domain schemas or carefully grouped namespaces (e.g. platform, school_core, academics, school_finance, cms_private, communications, restricted, xen_billing, ops). Avoid exposing restricted schemas via browser-facing API. A separate safe public read model/view schema may be selectively exposed, with explicit publication controls.

Alternative: one schema with table naming prefixes. Simpler initial migrations, but boundaries are less visible. Whichever is selected, separation is logical and does not replace RLS or permissions.

### TDR-04 — Authentication
Use managed Auth, linked by stable provider user UUID. Profile/person records remain separate from auth identity. Never store passwords, refresh tokens, provider secrets or raw session credentials in app tables. Account deletion/deactivation must coordinate membership revocation, audit and lawful retention.

### TDR-05 — API boundary
**Recommend:** browser uses authenticated application APIs for sensitive actions, backed by Cloudflare Workers. RLS and database grants remain defense in depth. Direct client-to-database/API access may be permitted for carefully selected low-risk operations only after reviewing its RLS, views, RPC and exposure. Do not let privileged server credentials reach the browser.

**Trade-off:** API-first increases engineering work but gives centralized validation, rate limits, audit, idempotency, and provider integrations. Direct access is faster to develop but requires precise RLS and API exposure discipline.

## 2. Migration and database standards

### TDR-06 — Migration tooling
**Recommend:** Supabase CLI migration files stored in Git. Every change gets review, migration replay from empty DB, tests, staging run and release approval. Avoid dashboard-only changes that create schema drift; document emergency changes and reconcile them into version control.

Migration practices:
- Atomic small migrations; expand/contract for breaking changes.
- Never run destructive production migration without backup, recovery plan and approval.
- Maintain schema diff/drift detection.
- Keep migrations idempotent only where tooling requires; otherwise migration ledger guarantees ordered single execution and scripts fail clearly if rerun.
- Seed/test data is synthetic and contains no personal information.

### TDR-07 — UUIDs
**Recommend for initial version:** UUIDv4, generated in DB or trusted server, compatible with PostgreSQL and auth IDs. UUIDv7 can improve insertion locality and time ordering, but may depend on runtime/version and can reveal approximate creation time. Revisit only after supported generators and security/privacy implications are validated. Never use sequential integers as public identifiers.

### TDR-08 — Tenant context
Tenant context must be derived from the authenticated user and active membership. A client-provided school identifier selects a context only; server must confirm membership and permission. Role/scope grants should be evaluated against database records and validity dates, not accepted from stale client claims. Membership revocation should take effect immediately or within a documented cache invalidation interval.

### TDR-09 — RLS helpers
Helpers may centralize active membership and permission checks, but:
- Set safe `search_path` and fully qualify referenced objects.
- Avoid SECURITY DEFINER unless justified, owner-controlled, audited and carefully restricted.
- No helper accepts a tenant ID and blindly returns true.
- Prevent recursive RLS design traps; consider reviewed security helper patterns.
- Use separate role/grant policies; fail closed on missing identity/context.
- Test helper with normal application roles, anonymous and cross-tenant IDs.
- Policy changes receive security review.

### TDR-10 — Time
Store instant timestamps as `timestamptz`, interpreted as UTC. Keep IANA timezone (e.g., Africa/Harare) as a setting for school/campus/user and event context. Use `date` for birthday, school calendar date, invoice due date, attendance date. Timetable local time needs timezone + date/context to resolve daylight saving in international deployments. Do not store ambiguous local timestamps.

### TDR-11 — Money
Use integer minor units plus currency code and a documented currency precision registry. Do not assume every currency uses 2 decimal places. Rounding rules are defined by operation and currency; preserve source and target amounts/rate for conversions. Never sum amounts across currencies without explicit conversion. Rates must be sourced/time-stamped and, where accounting policy requires, approved.

**Review required:** Zimbabwe currency policy (multi-currency and effective legal tender/configuration), payment reconciliation and currency rounding rules. Avoid hardcoding a single currency globally.

### TDR-12 — Finance separation
Keep school receivables/payments/ledger and XEN subscription billing in separate domain tables/schemas, permission sets, lifecycle and reporting. Shared provider transaction data may be linked through explicit integration IDs, not shared invoice/payment primary keys. Posted ledger data is immutable; use credit/reversal/journal entries.

## 3. Storage, publication, integrations and privacy

### TDR-13 — File storage
**Candidate:** Cloudflare R2 private buckets with Worker-mediated upload/download or signed access. Supabase Storage is also viable if integrated permissions and provider consolidation outweigh cross-platform needs. Decide after comparing cost, egress, signed URL support, scanning workflow, lifecycle/backup and operational simplicity.

File workflow: create metadata record → upload to quarantine → scan/type/size validation → mark clean → authorization for access → signed short-lived URL or Worker streaming → retention/deletion. Object key never contains names, student numbers or other PII. Public asset requires a distinct approval and public status.

### TDR-14 — CMS publishing
Authoring stays private. Publishing creates an explicit immutable version/publication record. Anonymous public read API/view selects only approved, published, current content and approved media for verified domain. Unpublish invalidates cache. No direct anonymous table grants; no private student/guardian/marks/finance/health/safeguarding joins. Media rights and consent must be recorded and reviewed.

### TDR-15 — Payments
Provider selection is not decided. Design a provider-neutral adapter with server-side verification, signed callbacks where available, idempotency keys, transaction reconciliation, refund/chargeback states and audit. Do not trust frontend success screens or webhook payloads without verification. Zimbabwe providers and international options require commercial/legal feasibility review, school market research and sandbox tests before integration.

### TDR-16 — Privacy/retention
Create a retention schedule for each data category and country/jurisdiction. Document purpose, lawful basis, consent where required, access, correction, retention, deletion/anonymization, legal hold, export and incident response. Children’s data and health/safeguarding data need special review. Do not invent universal retention durations; legal and school policy review is required.

### TDR-17 — Backups and disaster recovery
Confirm provider backup/PITR features for selected tier. Independently protect exports/backups with encryption and access controls. Test restoring into an isolated environment and validate counts/integrity, RLS, file references and application compatibility. Define RPO/RTO per module; recovery plans include auth, database, object storage, DNS and secrets.

### TDR-18 — Testing and CI
When implementation is authorized, use automated migration tests against a fresh PostgreSQL instance, plus realistic role/RLS tests, tenant isolation, integration/workflow, finance reconciliation, privacy, file security and API exposure tests. CI should never use production secrets. CI and workflow implementation are outside this review stage.

## 4. Deployment proposal

Current conceptual stack:
- Frontend: React + TypeScript, deployed to Vercel.
- API/backend: Cloudflare Workers, API-first.
- Database: Supabase PostgreSQL.
- Auth: Supabase Auth.
- Object storage: candidate Cloudflare R2.
- Git repository: GitHub.
- Tests: unit/integration with Vitest, browser acceptance with Playwright (tooling to confirm).

**Recommendation:** keep this as a proposed architecture, but minimize early complexity. A small team/budget should avoid duplicating responsibilities across platforms without clear value. Confirm actual needs and free-tier constraints before launch. No deployment is being performed in this review.
